# research — архитектура s3kn

Клиент S3 для Kotlin/Native, первый и главный таргет — **`linuxX64`**. Ниша ровно та же, что у
[kmp-smtp-client](https://github.com/youndie/kmp-smtp-client): сервису на Kotlin/Native сегодня
нечем сходить в объектное хранилище. AWS SDK for Kotlin — JVM-only (`aws.sdk.kotlin` публикует
только jvm-варианты), minio-java и aws-sdk-java не существуют вне JVM, а cinterop к `aws-c-s3`
тянет пять C-библиотек и всю их сборку на каждый таргет. Остаётся написать протокол самим —
и он для семи нужных операций небольшой: подпись SigV4 плюс семь HTTP-запросов с XML-ответами.

Объём v1 ограничен сознательно: **put, get, delete, head, list, multipart, presign**. Всё остальное
(ACL, теги, версии, lifecycle, SSE-C, S3 Express, SelectObjectContent) — потом.

Документ фиксирует **проверенные факты** (прочитанное в артефактах и в спецификации), **принятые
решения** и **риски**. Всё непроверенное помечено как гипотеза.

Копии спецификации лежат в [`docs/spec/`](../spec/) — ссылки вида
`docs/spec/reference/botocore-auth.py:538` указывают на строку в этой копии и читаются без сети.
Что именно там лежит и почему именно это — в [`docs/spec/README.md`](../spec/README.md).

## 1. Проверенные факты

### 1.1 HTTPS на linuxX64 даёт ровно один движок — `ktor-client-curl`

S3 — это HTTP поверх TLS. Всё остальное в этом ресёрче вторично: если нечем сделать
`https://`-запрос, библиотеки нет.

Проверено по опубликованным артефактам `io.ktor:*:3.5.2` (последняя версия на 2026-08-17,
`maven-metadata.xml`, `lastUpdated 20260731105638`).

| Факт | Где проверено |
|---|---|
| `ktor-client-cio` для `linuxX64` **зависит от `ktor-network-tls-linuxx64`** | `ktor-client-cio-linuxx64-3.5.2.pom`, блок `dependencies` |
| TLS в `ktor-network-tls` на native не реализован: `error("TLS sessions are not supported on Native platform.")` | `ktor-network-tls-linuxx64-3.5.2-sources.jar`, `nonJvmMain/io/ktor/network/tls/TLSClientSession.nonJvm.kt:18` |
| CIO-движок зовёт именно этот код на любом `https`-адресе | `ktor-client-cio-linuxx64-3.5.2-sources.jar`, `commonMain/io/ktor/client/engine/cio/Endpoint.kt:252` (`connection.tls(...)`) |
| `ktor-client-curl` публикует klib для `linux_x64`, `linux_arm64`, `macos_x64`, `macos_arm64`, `mingw_x64` | `ktor-client-curl-3.5.2.module`, поле `org.jetbrains.kotlin.native.target` |
| Cinterop-klib движка **несёт в себе статические libcurl, OpenSSL и nghttp2**: `staticLibraries.linux=libcurl.a libnghttp2.a libssl.a libcrypto.a`, и эти `.a` физически лежат внутри артефакта | `ktor-client-curl-linuxx64-3.5.2-cinterop-libcurl.klib`, `default/manifest` и `default/targets/linux_x64/included/` (16 МБ распакованного) |
| Версии внутри: **libcurl 8.20.0, OpenSSL 3.6.3** | `strings` по `libcurl.a` и `libcrypto.a` из того же klib |
| От системы движку нужен только `-lz` | там же, `linkerOpts.linux=-lz` |
| Путь к корневым сертификатам по умолчанию — `/etc/ssl/certs/ca-certificates.crt` | `strings` по `libcurl.a` |
| Переопределяется из конфига: `caInfo` (`CURLOPT_CAINFO`), `caPath` (`CURLOPT_CAPATH`), `sslVerify` | `ktor-client-curl-linuxx64-3.5.2-sources.jar`, `desktopMain/io/ktor/client/engine/curl/CurlClientEngineConfig.kt` |

**Следствие 1.** Развилки нет: на `linuxX64` HTTPS-движок один. Проектировать «на любом движке
Ktor» бессмысленно как цель, но получается бесплатно как побочный эффект — см. Р2.

**Следствие 2 — и это лучшая новость ресёрча.** Cinterop писать не нужно **вообще**. OpenSSL
приезжает уже собранный внутри klib'а Ktor, а не берётся из системы. Ровно та работа, которая
в kmp-smtp-client стоила отдельного модуля `smtp-tls-openssl` с поиском Homebrew/Debian-префиксов
и `-Wl,--allow-shlib-undefined`, здесь не возникает.

**Следствие 3 — цена.** Статический OpenSSL внутри klib'а означает, что обновление CVE в OpenSSL
приезжает **только с новой версией Ktor**, а не с `apt upgrade`. Это риск, см. Риск 1.

### 1.2 Криптография SigV4 — чистый Kotlin, cinterop не нужен

Первая мысль была взять HMAC-SHA256 и SHA256 из OpenSSL через cinterop — так на Kotlin/Native
обычно и приходится делать. Проверка показала, что не приходится.

Ближайший соседний проект того же автора,
[kmp-smtp-client](https://github.com/youndie/kmp-smtp-client), решает ту же задачу без cinterop;
его исходники — проверяемый источник, а не пример из головы.

| Факт | Где проверено |
|---|---|
| HMAC и хеши там берутся из **KotlinCrypto**, а не из OpenSSL: `HmacSHA256(key).doFinal(message)`, `SHA256().digest(data)` | kmp-smtp-client, `smtp-sasl/src/commonMain/kotlin/io/github/youndie/smtp/sasl/Crypto.kt` |
| Лежат они в **`commonMain`**, а не в нативном сорс-сете | тот же файл; `smtp-sasl/build.gradle.kts` подключает их в `commonMain.dependencies` |
| Cinterop к OpenSSL в том проекте существует, но только ради TLS: заголовки `ssl.h`, `err.h`, `bio.h`, `x509v3.h`, `opensslv.h`; `hmac.h`/`evp.h` там нет | kmp-smtp-client, `smtp-tls-openssl/src/nativeInterop/cinterop/openssl.def` |
| `org.kotlincrypto.macs:hmac-sha2` и `org.kotlincrypto.hash:sha2` версии 0.8.0 публикуют klib для `linuxX64` | листинг `repo1.maven.org/maven2/org/kotlincrypto/macs/hmac-sha2-linuxx64/` и `.../hash/sha2-linuxx64/`, `<release>0.8.0` |

**Следствие.** Модуль подписи получается **чистым Kotlin без единого cinterop**, а значит
компилируется на всех таргетах KMP, включая js и wasm. Отсюда прямо вытекает Р3: presign работает
везде, даже там, где HTTP-движка для нас нет.

### 1.3 Что требует SigV4 и чем S3 отличается от прочих сервисов

Проверено по эталонной реализации AWS — `botocore/auth.py`, копия в
[`docs/spec/reference/botocore-auth.py`](../spec/reference/botocore-auth.py). Это не «доки по
памяти»: это код, которым подписывает запросы `aws-cli`.

| Факт | Где проверено |
|---|---|
| Canonical request = `METHOD\nPATH\nQUERY\nCANONICAL_HEADERS\n\nSIGNED_HEADERS\nPAYLOAD_HASH` | `botocore-auth.py:370` |
| String to sign = `AWS4-HMAC-SHA256\n<timestamp>\n<date>/<region>/<service>/aws4_request\nhex(sha256(canonical_request))` | `botocore-auth.py:405` |
| Ключ = `HMAC(HMAC(HMAC(HMAC("AWS4"+secret, date), region), service), "aws4_request")`, подпись — hex от `HMAC(ключ, string_to_sign)` | `botocore-auth.py:417` |
| Формат метки времени — `%Y%m%dT%H%M%SZ`, дата в scope — первые 8 символов той же строки | `botocore-auth.py:63`, `:389` |
| Хеш пустого тела — константа `e3b0c442…b855` | `botocore-auth.py:55` |
| Canonical query: каждый ключ и значение кодируются с `safe='-_.~'`, пары сортируются **по закодированному ключу**, при равных ключах — по значению | `botocore-auth.py:268` |
| `host` берётся lowercase, порт отбрасывается, если он дефолтный для схемы | `botocore-auth.py:81` |
| Есть чёрный список никогда не подписываемых заголовков: `connection`, `expect`, `keep-alive`, `proxy-*`, `te`, `trailer`, `transfer-encoding`, `upgrade`, `user-agent`, `x-amzn-trace-id` | `botocore-auth.py:64` |
| **S3 не нормализует путь**: `_normalize_url_path` переопределён и возвращает путь как есть | `botocore-auth.py:538` — комментарий `# For S3, we do not normalize the path.` |
| Для всех прочих сервисов путь и нормализуется (убираются `.`/`..`), и **кодируется повторно**: `quote(normalize_url_path(path), safe='/~')` | `botocore-auth.py:385` |
| S3 всегда проставляет `X-Amz-Content-SHA256` — это не опция | `botocore-auth.py:490` |
| S3 **умеет** не хешировать тело, подставляя `UNSIGNED-PAYLOAD`, но по умолчанию хеширует — см. поправку ниже | `botocore-auth.py:497` вместе с `:334` |
| Presign: параметры `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Expires`, `X-Amz-SignedHeaders`, при временных ключах `X-Amz-Security-Token`; `X-Amz-Signature` **дописывается последним и в подпись не входит** | `botocore-auth.py:722`, `:787` |
| Для presign тело всегда `UNSIGNED-PAYLOAD` — на момент подписи оно неизвестно | `botocore-auth.py:810` |
| Дефолт `X-Amz-Expires` — 3600 | `botocore-auth.py:714` |
| Потолок `X-Amz-Expires` — 604 800 секунд (7 суток) | `smithy-typescript`, `packages/signature-v4/src/constants.ts`, `MAX_PRESIGNED_TTL = 60 * 60 * 24 * 7` |

**Следствие 1 — главное для формы API.** Раз S3 не нормализует и не перекодирует путь, подпись
считается **ровно по той строке пути, которая уйдёт на провод**. Значит кодирование ключа объекта
(`my dir/файл+v2.txt` → `/my%20dir/%D1%84%D0%B0%D0%B9%D0%BB%2Bv2.txt`) обязано быть **одной
функцией**, которую зовут и подписывальщик, и построитель URL. Две независимые реализации
кодирования разъедутся на первом же ключе с пробелом, и разъедутся молча: сервер ответит
`SignatureDoesNotMatch`, ничего не сказав про причину.

**Следствие 2.** Две эталонные реализации AWS **расходятся** в списке неподписываемых заголовков:
`smithy-typescript` дополнительно исключает `cache-control`, `from`, `max-forwards`, `pragma`,
`referer` и всё по шаблонам `^proxy-`/`^sec-`. Раз сами AWS не сошлись, опираться на «правильный
чёрный список» нельзя. Рабочее правило: **подписывать только те заголовки, которые выставили мы
сами** (`host`, `x-amz-*`, `content-type`, `content-length`, `content-md5`), и не подписывать
ничего, что мог добавить движок или прокси.

**Следствие 3.** `UNSIGNED-PAYLOAD` — не оптимизация, а единственный способ отдать поток. Хеш
тела нужен **до** отправки первого байта; если тело считать, его придётся сначала прочитать
целиком. Для 5-гигабайтного объекта это либо файл на диске, прочитанный дважды, либо 5 ГБ в RAM.
Отсюда Р6.

**Поправка, найденная при реализации M3.** Строка выше сначала утверждала, что botocore для S3
подставляет `UNSIGNED-PAYLOAD` на потоковых загрузках **по умолчанию**. Это неверно, и выяснилось
это при попытке получить от него такой вектор: `_should_sha256_sign_payload` (`:497`) сперва
смотрит в конфиг клиента, а не найдя там ничего, доходит до

```python
if not request.url.startswith("https") or checksum_header not in request.headers:
    return True
```

и возвращает `True`. То есть ветка «поток → не подписывать» (`has_streaming_input`) достижима
только когда рядом есть заголовок контрольной суммы. У обычного запроса его нет, и botocore тело
хеширует; чтобы он подставил константу, приходится задать `s3.payload_signing_enabled = False`
в конфиге клиента — именно это и делает генератор векторов.

На Р6 это не влияет, но меняет её обоснование: не «так делает botocore по умолчанию», а «поток
негде хешировать, а S3 это прямо разрешает». Современные SDK попадают в ту же ветку лишь потому,
что с 2025 года сами добавляют CRC32-заголовок (см. Открытый вопрос 2).

### 1.4 Официальный набор векторов существует, и он лежит в репозитории

| Факт | Где проверено |
|---|---|
| AWS публикует набор тестовых векторов SigV4; botocore вендорит его целиком под Apache 2.0 с `NOTICE` «AWS Signature Version 4 Test Suite, Copyright 2019 Amazon.com» | [`docs/spec/aws-sig-v4-test-suite/NOTICE`](../spec/aws-sig-v4-test-suite/NOTICE), `LICENSE` |
| 34 кейса; каждый — пять файлов: `.req` (сырой HTTP-запрос), `.creq` (ожидаемый canonical request), `.sts` (ожидаемый string to sign), `.authz` (ожидаемый заголовок `Authorization`), `.sreq` (запрос с подставленным заголовком) | `find docs/spec/aws-sig-v4-test-suite -name '*.req'` |
| Фиксированные входные данные: ключ `AKIDEXAMPLE`, секрет `wJalrXUtnFEMI/K7MDENG+bPxRfiCYEXAMPLEKEY`, время `20150830T123600Z`, регион `us-east-1`, сервис `service` | `botocore/tests/unit/auth/test_sigv4.py:41-43` |
| Кейсы покрывают ровно те места, где реализация ломается: UTF-8 в пути (`get-utf8`), пробел в пути (`normalize-path/get-space`), порядок и регистр ключей query (`get-vanilla-query-order-*`), повторяющиеся заголовки (`get-header-key-duplicate`), сворачивание многострочных значений (`get-header-value-multiline`), обрезка пробелов (`get-header-value-trim`), временный токен (`post-sts-token/*`) | листинг `docs/spec/aws-sig-v4-test-suite/` |
| 8 из 34 кейсов лежат в `normalize-path/` и проверяют **нормализацию пути**: `/./` → `/`, `/example space/` → `/example%20space/` | `docs/spec/aws-sig-v4-test-suite/normalize-path/get-slash-dot-slash/*.creq`, `.../get-space/*.creq` |
| Сам botocore четыре кейса из набора не гоняет: `normalize-path/get-space` (ломается его HTTP-парсер) и `get-vanilla-query-order-key`, `get-vanilla-query-order-key-case`, `get-vanilla-query-order-value` (повторяющиеся ключи query «не поддерживаются SDK») | `botocore/tests/unit/auth/test_sigv4.py:53-58` |

**Следствие 1 — это готовый TDD-скелет.** Первая веха пишется не «по здравому смыслу», а
прогоном 34 кейсов: тест читает `.req`, строит canonical request и сверяет с `.creq`, потом
string to sign с `.sts`, потом заголовок с `.authz`. Красный тест указывает не на «что-то не
сходится», а на конкретный шаг из трёх.

**Следствие 2 — и его надо понять до, а не после.** Набор проверяет **общий** SigV4, а S3 от
него отличается ровно в правиле пути (факт 1.3). Значит подписывальщик раскладывается на две
части: общее ядро, которое обязано пройти все 34 кейса, и S3-режим, отличающийся **одной**
подстановкой пути. Кейсы `normalize-path/*` в S3-режиме дадут другой ответ — и это не баг,
а ровно то, что надо закрепить отдельным тестом с ссылкой на `botocore-auth.py:538`.

**Следствие 3.** Векторов для S3-режима у AWS нет. Их источник — MinIO в CI (Р9) и рукописные
кейсы на кодирование ключа, вытекающие из следствия 1.3.1.

### 1.5 Семь операций: что это на проводе

Проверено по машинной модели API S3, копия — [`docs/spec/s3-service-2.json`](../spec/s3-service-2.json)
(`botocore/data/s3/2006-03-01/service-2.json`, протокол `rest-xml`).

| Операция | Метод и URI | Строка в модели |
|---|---|---|
| put | `PUT /{Bucket}/{Key+}` | `s3-service-2.json:1353` |
| get | `GET /{Bucket}/{Key+}` | `:717` |
| delete | `DELETE /{Bucket}/{Key+}`, успех — **204** | `:329` |
| head | `HEAD /{Bucket}/{Key+}` | `:878` |
| list | `GET /{Bucket}?list-type=2` | `:1014` |
| multipart: create | `POST /{Bucket}/{Key+}?uploads` | `:108` |
| multipart: part | `PUT /{Bucket}/{Key+}?partNumber=N&uploadId=…` | `:1596` |
| multipart: complete | `POST /{Bucket}/{Key+}?uploadId=…` + XML в теле | `:32` |
| multipart: abort | `DELETE /{Bucket}/{Key+}?uploadId=…`, успех — **204** | `:18` |

| Факт | Где проверено |
|---|---|
| Параметры list — `prefix`, `delimiter`, `max-keys`, `continuation-token`, `start-after`, `fetch-owner`, `encoding-type` | `s3-service-2.json`, `shapes.ListObjectsV2Request.members` |
| Ответ list — XML с `IsTruncated`, `Contents`, `CommonPrefixes`, `KeyCount`, `NextContinuationToken` | `shapes.ListObjectsV2Output.members` |
| `ETag` части приезжает **заголовком** ответа `UploadPart`, а не в теле | `shapes.UploadPartOutput.members.ETag.location = header` |
| Номера частей — от 1 до 10 000 включительно | документация `UploadPart` в модели, `s3-service-2.json:1604` |
| `CompleteMultipartUpload` может вернуть **200 OK с ошибкой внутри тела**: «a 200 OK response can contain either a success or an error» | документация `CompleteMultipartUpload`, `s3-service-2.json:32` |
| Его же особые ошибки: `EntityTooSmall`, `InvalidPart`, `InvalidPartOrder`, `NoSuchUpload` — все с HTTP 400 | там же |
| Отсутствие `Content-Length` — отдельная ошибка `MissingContentLength` с кодом **411 Length Required** | `s3-service-2.json:4768` |
| Ключ объекта может содержать любой символ Unicode, включая непарсимые XML 1.0 (коды 0–10); лечится параметром `encoding-type=url`, после которого ключи в ответе приходят URL-кодированными | `shapes.EncodingType.documentation` |

**Следствие 1.** `HEAD` по определению не имеет тела, значит XML-ошибки в нём нет: `404` придётся
разбирать по статусу и заголовку `x-amz-request-id`, а не по коду ошибки S3. Модель ошибок должна
допускать «код неизвестен, статус известен» — иначе `head` несуществующего объекта даст
`NullPointerException` в парсере вместо `NoSuchKey`.

**Следствие 2.** «200 OK с ошибкой в теле» на `complete` означает, что успех **нельзя** определять
по статусу. Тело complete читается всегда, и решение принимается по имени корневого элемента:
`CompleteMultipartUploadResult` или `Error`. Это же требование делает потоковый разбор XML
ненужным: тела всех наших ответов маленькие и читаются целиком.

**Следствие 3.** `encoding-type=url` надо слать **всегда**, а не по флагу. Иначе ключ с байтом
0x01 сломает не наш парсер, а сам XML, и сломает его у пользователя в проде, а не в тестах.

### 1.6 Движок curl: три места, где он определяет форму API

Проверено по `ktor-client-curl-linuxx64-3.5.2-sources.jar`.

| Факт | Где проверено |
|---|---|
| Тело запроса отдаётся **потоком** через `CURLOPT_READFUNCTION` из `ByteReadChannel`, с `READFUNC_PAUSE`, пока данных нет | `desktopMain/io/ktor/client/engine/curl/internal/CurlCallbacks.kt`, `onBodyChunkRequested` |
| Длина тела берётся так: `body.contentLength ?: headers[Content-Length] ?: -1L` | `internal/CurlRaw.kt`, `toCurlRequest` |
| При `PUT` она уходит в `CURLOPT_INFILESIZE_LARGE`; значение `-1` для libcurl означает «длина неизвестна» → `Transfer-Encoding: chunked` | `internal/CurlMultiApiHandler.kt`, `setupMethod` |
| `HEAD` ставит `CURLOPT_NOBODY`, `DELETE` уходит через `CURLOPT_CUSTOMREQUEST` | там же |
| Движок **принудительно гасит** `Expect: 100-continue`, дописывая в список заголовков пустой `Expect:` | `internal/CurlAdapters.kt:191` |
| Весь ввод-вывод идёт на одном выделенном потоке `newSingleThreadContext("curl-dispatcher")`, запросы — через `curl_multi_*` | `CurlProcessor.kt` |
| Движок объявляет поддержку `HttpTimeoutCapability`, `WebSocketCapability`, `SSECapability` | `CurlClientEngine.kt` |
| `ktor-client-mock` публикует klib для `linuxX64` | `repo1.maven.org/maven2/io/ktor/ktor-client-mock-linuxx64/`, `<release>3.5.2` |

**Следствие 1.** Длина тела для `put` и `uploadPart` — **обязательный параметр API**, а не
удобство. Без неё Ktor подставит `-1`, libcurl перейдёт на chunked, а S3 ответит
`411 MissingContentLength` (факт 1.5). Ошибка при этом проявится не на маленьком тесте с
`ByteArray` (там длина известна), а на первом же настоящем потоке из файла.

**Следствие 2.** `Expect: 100-continue` погашен движком, и вернуть его нельзя — заголовок в
чёрном списке подписи в том числе. Значит на `PUT` в 5 ГБ ответ `403 SignatureDoesNotMatch` или
`AccessDenied` придёт **после** того, как все 5 ГБ уйдут в сеть. Смягчение — Риск 3.

**Следствие 3.** Один поток `curl-dispatcher` на движок — это потолок параллелизма для
многочастной загрузки. `curl_multi_*` мультиплексирует соединения на этом же потоке, так что
упрёмся мы, скорее всего, не в CPU, а в него. Гипотеза, мерить в вехе multipart (Риск 5).

### 1.7 Время берётся из stdlib, зависимость не нужна

| Факт | Где проверено |
|---|---|
| `kotlin.time.Clock` и `kotlin.time.Instant` **стабильны с Kotlin 2.3** — `@SinceKotlin("2.3")` + `@WasExperimental`, opt-in больше не требуется | `kotlin-stdlib-2.4.10-sources.jar`, `commonMain/kotlin/time/Clock.kt:18`, `Instant.kt:105` |
| `Instant` отдаёт `epochSeconds` и `nanosecondsOfSecond` | `Instant.kt:120`, `:130` |
| Календарного разложения в stdlib нет — только эпоха | там же, весь файл |
| `kotlinx-datetime` последней опубликованной версией показывает `0.8.0-0.6.x-compat` | `maven-metadata.xml` артефакта `org.jetbrains.kotlinx:kotlinx-datetime` |

**Следствие.** SigV4 нужен ровно один формат — `20150830T123600Z`, UTC, без часовых поясов и
локалей. Это 15 строк перевода epoch-дней в календарную дату; тянуть ради них `kotlinx-datetime`
в библиотеку не стоит. Заодно `Clock` становится параметром подписывальщика, и тест на векторах
получает фиксированное время без подмены глобалов.

### 1.8 Что уже есть у соседей и почему не подходит

| Вариант | Почему не берём |
|---|---|
| AWS SDK for Kotlin (`aws.sdk.kotlin:s3`) | проверено: версия 1.8.31 (`maven-metadata.xml`, `lastUpdated 20260814`) объявляет в `s3-1.8.31.module` только варианты `common` и `jvm`, артефакта `s3-linuxx64` не существует (404 на `repo1.maven.org/maven2/aws/sdk/kotlin/s3-linuxx64/`) |

| `system("aws s3 cp ...")` | требует установленного aws-cli в образе, не даёт ни потоков, ни кодов ошибок, presign через него — парсинг stdout |
| Свой HTTP поверх `ktor-network` | это ровно то, что упирается в факт 1.1: TLS на native нет |

## 2. Решения

### Р1. Раскладка на четыре модуля, зависимости только внутрь

```
:s3-core       модель, ошибки, конфиг, кодирование ключей, XML. Без I/O, без Ktor.
:s3-sigv4      подпись и presign. Чистый Kotlin, зависит только от :s3-core и KotlinCrypto.
:s3-client     семь операций поверх ktor-client-core. Знает про HttpClient, не знает про движок.
:s3-testing    фикстуры: загрузчик векторов, фейковые ответы, обвязка над MinIO.
```

Почему так, а не одним модулем: `:s3-sigv4` обязан собираться и проходить тесты **без сети и без
движка** — это единственный способ гонять 34 вектора на любом таргете и в CI за секунды. Как
только подпись и HTTP окажутся в одном модуле, тест подписи потянет за собой libcurl.

Отброшено: отдельный модуль `:s3-xml`. Разбор шести форм XML — это ~200 строк, отдельный модуль
для них создаёт публичную границу там, где её незачем поддерживать.

### Р2. `:s3-client` принимает готовый `HttpClient`, своего порта транспорта нет *(отклонение от образца)*

В kmp-smtp-client между клиентом и Ktor стоит собственный порт транспорта, а `ktor` встречается
ровно в одном модуле. Здесь — нет.

Почему:

- там Ktor давал **только сокет**, и HTTP-семантику всё равно писали сами; здесь Ktor даёт
  весь HTTP целиком, и свой порт поверх `HttpClient` был бы обёрткой над обёрткой;
- `HttpClientEngine` — это уже та самая точка подмены, ради которой заводят порт: curl на native,
  OkHttp/CIO на JVM, `MockEngine` в тестах, и `ktor-client-mock` для `linuxX64` опубликован
  (факт 1.6);
- пользователь получает свой таймаут, ретраи и логирование как обычные плагины Ktor, а не как
  наш параллельный набор настроек;
- цена: `:s3-client` зависит от `ktor-client-core` и его типов. Это осознанно. Взамен
  `:s3-sigv4` от Ktor не зависит вовсе, а именно там живёт вся содержательная часть.

Движок в зависимости библиотеки **не входит** — его выбирает приложение. В документации и в
`examples/` для `linuxX64` показывается `ktor-client-curl` как единственный рабочий выбор
(факт 1.1).

### Р3. Presign — чистая функция, а не метод клиента

`presign(method, bucket, key, expires)` не делает запросов и не нуждается в `HttpClient`. Живёт
в `:s3-sigv4`, возвращает строку URL.

Почему:

- подпись presign вообще не зависит от тела (`UNSIGNED-PAYLOAD`, `botocore-auth.py:810`), то
  есть от сети там нет ничего;
- следствие для сборки: `:s3-sigv4` — чистый Kotlin (факт 1.2), значит presign работает **на всех
  таргетах KMP**, включая js и wasm, где HTTP-движка для нас нет. Бэкенд на Kotlin/Native выдаёт
  ссылку, фронтенд на wasm её проверяет — обоим хватает одного модуля;
- цена: presign нельзя «просто позвать у клиента», конфиг придётся передать явно. Лечится тем,
  что и клиент, и presign принимают один и тот же объект конфигурации.

### Р4. Кодирование ключа — одна функция на подпись и на URL

Единственная реализация `uriEncodeKey(key: String): String` в `:s3-core`, которую зовут и
построитель URL, и подписывальщик. Прямое следствие 1.3.1.

Почему не «Ktor сам закодирует»: тогда строка в подписи и строка на проводе получаются двумя
разными кодировщиками с разными наборами safe-символов, и расхождение вылезет только на ключах
с `+`, пробелом, `~` или не-ASCII. Запрос к URL уходит уже закодированным (`url.encodedPath`),
чтобы Ktor его не трогал.

Правило кодирования — из `botocore-auth.py:268`: не кодируются `A-Za-z0-9-_.~`, `/` в пути
остаётся как есть, всё прочее — `%XX` заглавными, UTF-8.

### Р5. Общее ядро SigV4 + режим S3 одной подстановкой

`CanonicalRequest` строится общим кодом; путь в него подаёт стратегия: «нормализовать и
перекодировать» (общий SigV4) либо «взять как есть» (S3). Прямое следствие 1.4.2.

Почему не писать сразу только S3-вариант: тогда 34 официальных вектора нечем прогнать, и
единственной проверкой подписи останется MinIO, то есть «работает против одной реализации
сервера». Ядро с двумя режимами стоит один интерфейс из одного метода, а даёт готовый набор
приёмки.

### Р6. `UNSIGNED-PAYLOAD` по умолчанию для put и uploadPart, но только поверх https

Хеш тела считается, только если пользователь явно попросил (`signPayload = true`) или если схема
`http`.

Почему:

- посчитать sha256 тела — значит прочитать его целиком до отправки; для потока это либо второй
  проход по файлу, либо весь объект в памяти (следствие 1.3.3);
- S3 прямо разрешает эту подстановку, и botocore умеет её включать (`botocore-auth.py:497`) —
  но **не** делает этого по умолчанию, см. поправку к 1.3;
- поверх `http` подписывать тело обязательно — без TLS подпись заголовков не защищает содержимое;
- цена: при `http` + поток библиотека обязана **отказать явной ошибкой**, а не молча буферизовать
  гигабайты. Отказ с текстом «дай длину и разреши буферизацию либо включи https» — единственное
  честное поведение.

### Р7. Длина тела — обязательный параметр put и uploadPart

`put(key, body: ByteReadChannel, contentLength: Long)`. Перегрузка с `ByteArray` считает длину
сама. Прямое следствие 1.6.1: без длины — chunked, а на chunked S3 отвечает `411`.

### Р8. XML — свой разбор, без библиотеки

Пять форм на чтение — `ListBucketResult`, `Error`, `InitiateMultipartUploadResult`,
`CompleteMultipartUploadResult`, `ListPartsResult` — и одна на запись,
`CompleteMultipartUpload` (список `<Part><PartNumber/><ETag/></Part>`). Все плоские, тела мелкие
(следствие 1.5.2).

Почему не `xmlutil` (проверено: `io.github.pdvrieze.xmlutil:core` и `serialization` версии 1.0.2
публикуют `linuxx64`, так что вариант рабочий): он тянет плагин `kotlinx-serialization` и два
артефакта в библиотеку, у которой иначе одна зависимость на модуль. Для шести плоских форм это
несоразмерно.

Цена и **тревожная кнопка**: парсер наш, значит и его дыры наши. Как только понадобятся
`ListObjectVersions`, теги, ACL или `Delete` пачкой — форм станет вдвое больше и вложенность
вырастет; в этот момент решение пересматривается в пользу `xmlutil`, а не латается.

### Р9. Приёмка — векторы AWS плюс MinIO, зафиксированный по тегу

Два независимых уровня:

1. **Подпись** — 34 вектора из `docs/spec/aws-sig-v4-test-suite/`, без сети, на каждом таргете.
2. **Протокол** — MinIO из `docker-compose.yml`, `linuxX64` в CI.

MinIO пинится точным тегом. Проверено: `minio/minio:latest` на Docker Hub последний раз
обновлялся **2025-09-07** (`hub.docker.com/v2/repositories/minio/minio/tags`), то есть `latest`
давно не движется; полагаться на плавающий тег здесь нельзя ни в какую сторону. Берём
`RELEASE.2025-09-07T16-13-09Z`.

Открыто: MinIO — не S3. Что делать с расхождениями — Открытый вопрос 1.

### Р10. Тест раньше кода, и тест ссылается на строку спецификации

То же правило, что в kmp-smtp-client, с заменой RFC на `docs/spec/`:

> прочитать место в спецификации → красный тест → убедиться, что он красный по нужной причине →
> код → зелёный → `ktlintCheck`.

Тест подписи называет кейс: `` `get-utf8 case from aws-sig-v4-test-suite`  ``. Тест протокола
ссылается на строку модели: `s3-service-2.json:1604`. Тест «по здравому смыслу» не принимается —
в S3 здравый смысл говорит, что 200 значит успех (факт 1.5).

Отдельно, граблями из kmp-smtp-client: **запятая в имени теста в обратных кавычках ломает
Kotlin/Native** («Name contains illegal characters»), хотя JVM такое компилирует.

## 3. Риски и открытые вопросы

**Риск 1. OpenSSL внутри klib'а обновляется только вместе с Ktor.** В движке зашит статический
OpenSSL 3.6.3 (факт 1.1), и `apt upgrade` в образе на него не влияет. Смягчение: версия Ktor —
единственная строка в каталоге версий, её обновление обязано быть отдельной задачей в каждой
вехе; в `README` пишется, какой OpenSSL внутри текущей версии, чтобы это было видно без распаковки
klib'а. Проверять при каждом бампе Ktor: `strings` по `libcrypto.a`.

**Риск 2. Нет корневых сертификатов — тихий отказ.** Статический libcurl ищет их по
`/etc/ssl/certs/ca-certificates.crt` (факт 1.1), а в `scratch`/`distroless`-образе их нет, и
падение выглядит как ошибка соединения, а не как «поставь `ca-certificates`». Смягчение: в
`examples/` — `Dockerfile` с `ca-certificates`, и отдельный тест, который ходит по https к
реальному хосту **из образа**, а не с машины разработчика.

**Риск 3. Отказ по правам приходит после отправки всего тела.** `Expect: 100-continue` погашен
движком и вернуть его нельзя (следствие 1.6.2). Смягчение: многочастная загрузка начинается с
`CreateMultipartUpload`, который сам по себе — дешёвая проверка прав и существования бакета;
для одиночного `put` в документации явно сказано, что валидация доступа делается вызывающим
(например, `head` по бакету), и почему.

**Риск 4. Расхождение кодировщиков ключа даёт `SignatureDoesNotMatch` без объяснений.** Смягчение
архитектурное — Р4 (одна функция), плюс тесты на ключи с пробелом, `+`, `~`, кириллицей,
эмодзи и `//` подряд, гоняемые против MinIO. Плюс: при получении `SignatureDoesNotMatch`
библиотека кладёт в исключение **свой** canonical request — S3 в теле ошибки присылает тот,
который посчитал он, и построчное сравнение находит причину за минуту.

**Риск 5. Один поток `curl-dispatcher` — потолок многочастной загрузки.** Гипотеза (следствие
1.6.3): параллельные части упрутся в него раньше, чем в сеть. Проверить замером в вехе multipart:
1 / 4 / 16 параллельных частей по 8 МБ, смотреть на суммарную пропускную способность, а не на
время одной части. Если потолок подтвердится — вариант выхода — несколько `HttpClient`, каждый со
своим движком и своим потоком; это дороже по памяти и должно быть решением, а не случайностью.

**Риск 6. `complete` вернул 200, а внутри ошибка.** Смягчение: разбор по корневому элементу
(следствие 1.5.2) и тест, который эту ситуацию воспроизводит через `MockEngine` — от MinIO её
не добьёшься по заказу.

**Риск 7. Ошибки без тела.** `HEAD` не имеет тела вовсе, а некоторые прокси и S3-совместимые
хранилища отвечают пустым телом и на других методах. Смягчение: модель ошибки допускает
отсутствие кода S3, и в этом случае несёт статус, `x-amz-request-id` и `x-amz-id-2` —
без них поддержка AWS разговаривать не станет.

**Открытый вопрос 1. Чем закрывать расхождения MinIO и настоящего S3.** MinIO покрывает
протокол, но не гарантирует одинакового поведения в мелочах (кодирование ключей в `ListObjectsV2`,
точный текст ошибок, поведение на `encoding-type=url`). Гипотеза: держать отдельный набор тестов
с меткой «требует настоящий S3», не гоняемый в CI по умолчанию, и прогонять его руками перед
релизом. Решать после первой вехи с `list`.

**Открытый вопрос 2. Нужны ли контрольные суммы.** С 2025 года AWS SDK по умолчанию считают
CRC32 и шлют `x-amz-checksum-crc32`; модель знает десять алгоритмов
(`shapes.UploadPartRequest.members`). Для v1 не берём: `UNSIGNED-PAYLOAD` поверх TLS уже даёт
целостность канала, а CRC потребует своей реализации на Kotlin/Native. Пересмотреть, если
появится требование сквозной проверки объекта после записи.

**Открытый вопрос 3. Регион и endpoint.** Для AWS адресация виртуальными хостами
(`bucket.s3.region.amazonaws.com`), для MinIO и локальных развёрток — path-style
(`host:9000/bucket/key`). Стиль **обязан** быть явным параметром конфигурации, потому что от него
зависит заголовок `host`, а он входит в подпись. Гипотеза: автоопределение («AWS-домен →
virtual-hosted, иначе path-style») удобно, но угадывает; в v1 — явный флаг с разумным значением
по умолчанию, автоопределение не делаем.

## 4. Что делать дальше

Порядок работ и приёмка — в [BACKLOG.md](../../BACKLOG.md).

Раньше всего фиксируется то, от чего зависит всё остальное:

1. **Кодирование ключа** (Р4) — одна функция, свои векторы. Она входит и в подпись, и в URL;
   ошибка здесь портит все семь операций сразу.
2. **Ядро SigV4 на 34 векторах** (Р5, факт 1.4) — без сети, без движка. Это единственное место
   в проекте, где есть готовая внешняя приёмка, и её надо получить до первого HTTP-запроса.
3. **Первый живой запрос — `head`** против MinIO. Самая дешёвая операция, которая при этом
   проверяет всю цепочку: конфиг → адресация → подпись → движок → TLS → разбор ошибок без тела
   (Риск 7).

Только после этого имеет смысл `put`/`get`, потому что до этого момента любое их падение
неотличимо от ошибки подписи.
